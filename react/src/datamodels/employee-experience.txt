Employee Experience Tab — API Endpoint & Data Model Specification
=====================================================================
Base Path: /api/employee-experience

All endpoints below are derived from the existing mock-data service layer
(`src/services/employeeExperienceService.ts`) and the shared type definitions
(`src/types/index.ts`).  Use this document to wire up real server endpoints.

-----------------------------------------------------------------------------
1. SELF-SERVICE REQUESTS
-----------------------------------------------------------------------------
GET    /self-service?employeeId={employeeId}
       → Response: SelfServiceRequest[]

POST   /self-service
       Body:
       {
         "type": "address-change" | "benefits" | "payroll" | "equipment" | "leave-request" | "other",
         "subject": string,
         "details": string,
         "priority": "low" | "medium" | "high"   // optional, default "medium"
       }
       → Response: SelfServiceRequest

--- Type: SelfServiceRequest ---
{
  "id": string,
  "employeeId": string,
  "employeeName": string,
  "type": "address-change" | "benefits" | "payroll" | "equipment" | "leave-request" | "other",
  "subject": string,
  "details": string,
  "status": "submitted" | "in-review" | "in-progress" | "resolved" | "rejected",
  "priority": "low" | "medium" | "high",        // optional
  "assignedTo": string | null,                    // optional
  "createdAt": string,                          // ISO 8601
  "updatedAt": string | null,                   // optional
  "attachments": string[]                       // optional
}

5. CAREER DEVELOPMENT PLANS
-----------------------------------------------------------------------------
GET    /career-plans?employeeId={employeeId}
       → Response: CareerDevelopmentPlan[]

PATCH  /career-plans/{planId}/milestones/{milestoneId}
       Body:
       {
         "status": "not-started" | "in-progress" | "completed" | "blocked"
       }
       → Response: CareerDevelopmentPlan   // full plan with recalculated status

--- Type: CareerMilestone ---
{
  "id": string,
  "planId": string,
  "title": string,
  "targetDate": string,           // yyyy-mm-dd
  "status": "not-started" | "in-progress" | "completed" | "blocked",
  "evidenceLink": string | null     // optional
}

--- Type: CareerDevelopmentPlan ---
{
  "id": string,
  "employeeId": string,
  "employeeName": string,
  "managerId": string,
  "currentRole": string,
  "targetRole": string | null,      // optional
  "horizon": "6-months" | "12-months" | "24-months",
  "status": "draft" | "on-track" | "at-risk" | "completed" | "stalled",
  "milestones": CareerMilestone[],
  "lastReviewedAt": string | null   // optional, ISO 8601
}

Server-side recalculation rules (from current client logic):
  • If ALL milestones "completed" → plan.status = "completed"
  • If ANY milestone "blocked"     → plan.status = "stalled"
  • If ANY milestone "in-progress" → plan.status = "on-track"
  • Otherwise                      → plan.status stays as-is or "draft"

9. KANBAN ITEMS
-----------------------------------------------------------------------------
GET    /kanban
       → Response: KanbanItem[]
       (Filter server-side or client-side by sourceType / assigneeId as needed)

PATCH  /kanban/{id}/lane
       Body:
       {
         "lane": "backlog" | "in-progress" | "in-review" | "done"
       }
       → Response: KanbanItem
       Side effect: sync underlying entity status (see mapping below)

--- Type: KanbanItem ---
{
  "id": string,
  "sourceType": "self-service" | "pulse-feedback" | "recognition" | "career" | "learning" | "issue" | "delay",
  "sourceId": string,               // ID of the originating entity
  "title": string,
  "lane": "backlog" | "in-progress" | "in-review" | "done",
  "assigneeId": string | null,       // optional
  "priority": "low" | "medium" | "high" | "critical",  // optional
  "dueDate": string | null,            // optional, yyyy-mm-dd
  "tags": string[],                   // optional
  "updatedAt": string                 // ISO 8601
}

Status sync mapping (lane → underlying entity status):
  • backlog      → "submitted"
  • in-progress  → "in-progress"
  • in-review    → "in-review"
  • done         → "resolved"

For SelfServiceRequest the status field accepts:
  "submitted" | "in-review" | "in-progress" | "resolved" | "rejected"

For IssueReport the status field accepts:
  "submitted" | "acknowledged" | "in-progress" | "resolved" | "wont-fix"
  (When lane = done, also set resolvedAt = now)

For DelayConcern the status field accepts:
  "open" | "acknowledged" | "resolved" | "rejected"

CURRENT USER (showcase hard-coding)
-----------------------------------------------------------------------------
The client currently assumes:
  employeeId = "emp_4521"
  employeeName = "Ava Thompson"
  managerId  = "emp_4490"

For a real API, derive the current user from the auth token / session
instead of passing it in query params for every call.

However, the GET list endpoints above accept an explicit employeeId
parameter so the same routes can support managers viewing their reports.
